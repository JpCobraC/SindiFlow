## Objetivo desta Sessão

Analisar as **lacunas da proposta do projeto** antes de iniciar a implementação, focando em decisões que precisam ser tomadas para garantir que o MVP respeite as obrigações técnicas do projeto.

As obrigações técnicas consultadas estão em `agent_tools/sindiflow-obrigacoes.md` (v1.0), que define como "lei superior" do projeto:

- Expo SDK 54 nativo, sem web
- SQLite como fonte da verdade para dados offline
- Toda escrita passa pela fila de **outbox** com retry exponencial
- Detecção de rede via `expo-network`
- Câmera + FileSystem para evidências, geolocalização por sessão de vistoria
- Clean Architecture estrita: Domain → Application → Adapters → Infra
- TDD obrigatório (red → green → refactor)
- Revisão pré-implementação com self-correction loop (§4.2)

## Fase 2 — Análise da Lacuna 1 (Autenticação)

### Por que esta lacuna é crítica

A autenticação não é apenas "ter login". É necessário definir **como a identidade do usuário será comprovada e preservada durante o uso offline**, pois isso afeta:

- Atribuição de `usuario_id` em vistorias e chamados
- Auditoria e conformidade com LGPD
- Regras por perfil (`síndico`, `zelador`, `administrador`)
- Row Level Security (RLS) no Supabase
- Resolução de conflitos durante o sync
- Uso do aplicativo antes da primeira conexão

### Opções de autenticação apresentadas

#### Opção A — Anônimo por condomínio

O usuário informa apenas o condomínio e recebe uma sessão/dispositivo local.

| Prós | Contras |
|------|---------|
| Implementação mais rápida | Sem identidade real do usuário |
| Funciona totalmente offline desde o primeiro uso | Auditoria fraca |
| Ideal para protótipo/demo | Não suporta múltiplos usuários ou dispositivos |
| Menor complexidade de UX | RLS no Supabase fica limitado |

#### Opção B — PIN local/offline

Cada condomínio ou usuário possui um PIN cadastrado e validado localmente.

| Prós | Contras |
|------|---------|
| Simples e rápido para o usuário | Segurança inferior a serviço de autenticação |
| Funciona sem rede | Compartilhamento de PIN prejudica responsabilização |
| Baixa dependência de infraestrutura | Revogação e troca exigem estratégia online |
| Bom para equipe pequena e conhecida | Não resolve múltiplos perfis adequadamente |

#### Opção C — Supabase Auth online + sessão em cache

Login pelo Supabase Auth quando houver rede; usuário, perfil e sessão ficam cacheados para uso offline.

| Prós | Contras |
|------|---------|
| Autenticação madura e centralizada | Primeiro login exige conexão |
| Integração natural com Supabase | Expiração de token precisa de tratamento offline |
| Permite RLS e autorização por usuário | Usuário revogado pode continuar offline até reconectar |
| Recuperação de senha e gestão de usuários existentes | Maior complexidade de implementação |
| Melhor base para produção | Necessita armazenamento seguro da sessão |

#### Opção D — Híbrida: Supabase Auth + janela offline controlada

Login e validação pelo Supabase; app mantém janela offline limitada com usuário, perfil e permissões cacheados. Ao reconectar, valida a sessão e sincroniza a fila.

| Prós | Contras |
|------|---------|
| Melhor equilíbrio entre segurança e offline-first | Maior complexidade arquitetural |
| Mantém auditoria e RLS | Necessita definir prazo máximo offline |
| Suporta múltiplos usuários e dispositivos | Revogação de acesso precisa de regra explícita |
| Funciona em áreas sem sinal após login prévio | Mais cenários de teste |
| Escala melhor para produção | Pode consumir mais horas do budget |

### Veredito sobre a Opção C e Offline First

A Opção C **respeita o Offline First**, pois:

1. SQLite permanece como fonte da verdade local, independente do Auth
2. O usuário pode realizar toda a vistoria offline após o login inicial
3. O sync ocorre assíncronamente quando a rede retorna
4. O ciclo TDD red-green-refactor se aplica normalmente

**Restrições da Opção C:**

- Primeiro login exige rede
- Expiração de token precisa de estratégia de refresh/caching
- Usuário revogado pode continuar operando offline até reconectar
- RLS precisa funcionar com sessão cacheada

**Recomendação:** Opção C é o melhor equilíbrio para o MVP com 60h, desde que o primeiro uso com conexão seja garantido.

## Fase 3 — Perguntas para Fechar a Opção C

Foram levantadas **8 categorias de perguntas** para detalhar a Opção C antes da implementação.

### 1. Onboarding / Primeiro login

- O usuário já tem conta no Supabase (convite/admin cria) ou faz signup no app?
- Se há convite: como o admin envia? (e-mail, link mágico, código)
- O app permite criar a primeira vistoria antes do primeiro sync?

### 2. Sessão offline

- Qual o tempo máximo offline permitido? (ex: 7, 30, 90 dias)
- O que acontece ao expirar a sessão offline? (bloquear tudo, permitir concluir vistoria, apenas avisar)
- Refresh token é armazenado? Como é renovado ao reconectar?

### 3. Perfil e permissões

- Os perfis (`síndico`, `zelador`, `admin`) vêm do Supabase Auth (custom claims/metadata) ou de tabela própria?
- Permissões mudam durante o uso offline?
- Um mesmo dispositivo pode ter múltiplos usuários?

### 4. Segurança do armazenamento local

- Sessão (access/refresh token, user id, perfil) fica em SQLite encriptado ou SecureStore/Keychain?
- Dados do usuário (nome, e-mail, condomínio) são cacheados para exibição offline?

### 5. Outbox e identificação do autor

- Cada entrada da fila outbox carrega `usuario_id` + `device_id`?
- Operações feitas offline por usuário revogado no Supabase: como são tratadas no sync?

### 6. Fluxo de "primeiro uso sem rede" (edge case)

- Se o usuário abre o app pela primeira vez sem internet, o que acontece?
  - Tela de erro orientando conectar
  - Modo "visitante" limitado
  - Outro

### 7. Logout e troca de usuário

- Logout limpa todo o SQLite ou apenas a sessão?
- Troca de usuário no mesmo dispositivo: mantém dados do anterior ou limpa?

### 8. Supabase — configuração prática

- URL e anon key já estão disponíveis?
- RLS policies já definidas nas tabelas?
- Haverá admin panel separado ou admin usa o mesmo app?

### Definition of Ready para começar a implementar

| Item | Status |
|------|--------|
| Origem da conta (convite vs signup) | Pendente |
| Tempo máximo offline | Pendente |
| Armazenamento seguro da sessão | Pendente |
| Perfil/permissões: fonte (custom claims vs tabela) | Pendente |
| Outbox carrega `usuario_id` + `device_id` | Pendente |
| Comportamento ao expirar sessão offline | Pendente |
| URL/key do Supabase | Pendente |

## Fase 4 — Decisões do Usuário sobre a Opção C

O usuário respondeu a todas as 8 categorias de perguntas, definindo os seguintes parâmetros:

### 1. Onboarding / Primeiro login

**Decisão:** Convite pelo admin (por exemplo, um morador novo é convidado pelo síndico), por e-mail.

- O síndico (admin) envia convite por e-mail para novos moradores/usuários
- O usuário aceita o convite e cria/ativa sua conta
- **Observação:** foi solicitado ao agente que desse a melhor sugestão, visto que o usuário não entendeu bem o mecanismo

### 2. Sessão offline

**Decisão:** 7 dias.

- Avisa **1 dia antes** de expirar a sessão
- Ao expirar, **bloqueia tudo** para re-logar
- **Sugestão do agente:** seguir `agent_tools/sindiflow-obrigacoes.md` — a decisão está alinhada com as obrigações, pois o bloqueio total é mais seguro que permitir operações com sessão expirada

### 3. Perfil e permissões

**Decisão:** Tabela própria.

- Perfis (`síndico`, `zelador`, `admin`) serão armazenados em **tabela própria** no banco
- Será necessário o uso de **SQL** para gerenciar permissões
- **Não** haverá mudança de permissões durante o uso offline
- **Não** haverá múltiplos usuários no mesmo dispositivo

### 4. Segurança do armazenamento local

**Decisão:** O usuário não soube responder sobre o mecanismo de armazenamento seguro.

- Dados do usuário serão **cacheados para exibição offline**
- **Ponto aberto:** definir onde e como a sessão será armazenada com segurança (SQLite encriptado vs SecureStore/Keychain)

### 5. Outbox e identificação do autor

**Decisão:** Sim, cada entrada carrega `usuario_id` + `device_id`.

- Operações feitas offline por usuário **revogado** serão **notificadas e rejeitadas** no sync

### 6. Primeiro uso sem rede

**Decisão:** Opção C pura basta.

- Não haverá modo visitante ou fallback offline para primeiro uso
- O app exigirá conexão para o primeiro login/aceite de convite

### 7. Logout e troca de usuário

**Decisão:** Apenas a sessão é limpa.

- Dados de vistoria são **mantidos** no SQLite
- O app **bloqueia** novas operações até o re-login

### 8. Supabase — configuração prática

**Decisão:** Admin usa o mesmo app.

- Não há admin panel separado
- **Nada está disponível ou definido ainda** para Supabase (URL, key, schema, RLS)
- **Fase atual:** planejamento/proposta, nada implementado

## Fase 5 — Validação das Decisões contra `agent_tools/sindiflow-obrigacoes.md`

### ✅ Decisões alinhadas com as obrigações

| Decisão | Verificação | Observação |
|---------|-------------|------------|
| Convite por admin via e-mail | ✅ Compatível | Não viola obrigações; define fluxo de entrada claro |
| 7 dias offline, aviso 1 dia antes, bloqueio total | ✅ Alinhado | Respeita sessão cacheada; bloqueio total é mais seguro |
| Outbox com `usuario_id` + `device_id` + rejeição de revogados | ✅ Obrigatório | Cumpre requisitos de auditoria e segurança (Seção 1.3 e 3.3) |
| Logout limpa apenas sessão, mantém dados, bloqueia até re-login | ✅ Seguro | Dados permanecem em SQLite (fonte da verdade) |
| Admin usa o mesmo app | ✅ Compatível | Não viola obrigações |

### ⚠️ Pontos que necessitam esclarecimento antes da implementação

#### Ponto 1 — Armazenamento seguro da sessão (decisão #4)

**Pergunta crítica:** Que dados serão cacheados? Nome, e-mail, condomínio, foto de perfil?

**Riscos se não definido:**

- Armazenar e-mail/nome em texto viola LGPD se não encriptado
- Cachear excesso aumenta superfície de ataque
- Não cachear prejudica UX (tela de boas-vindas vazia)

**Recomendação:**

- Cachear apenas identificador non-PII (ex: `user_id` hash) + nome de exibição limitado
- Armazenar em SQLite com campos marcados como sensíveis (não em AsyncStorage)
- Aplicar princípio de mínimo privilégio: só o estritamente necessário para UI offline

#### Ponto 2 — Tabela própria para perfis (decisão #3)

**Verificação de Clean Architecture:**

- ✅ **Permissível** se:
  - A tabela for criada em `infra/` ou `adapters/repositories/`
  - O acesso ocorrer exclusivamente através de interface em `domain/` (ex: `UserRepository`)
  - Nenhuma regra de negócio ficar na camada de infraestrutura
- ❌ **Violação** se:
  - SQL direto aparecer em `application/` ou `domain/`
  - Regras de permissão estiverem em queries SQL ao invés de entidades/domain services

#### Ponto 3 — Opção C pura (decisão #6)

**Validação necessária:**

- O projeto aceita que usuários sem conexão prévia não possam usar o app?
- Se não, é necessário definir modo "convidado" com limitações ou fluxo de onboarding alternativo
- Documentar essa limitação para evitar expectativas equivocadas
