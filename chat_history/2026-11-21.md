## Objetivo desta Etapa (D-3)

Integrar a renovação de access token expirado no boot, usando o refresh token
persistido no Supabase, evitando logout desnecessário quando a sessão ainda é
renovável. Seguindo `agent_tools/sindiflow-obrigacoes.md` v1.3.1 (TDD, ordem
estrita de camadas, sem commit/push pelo agente).

---

## O que foi feito

### Interface (Domain)

- Adicionado `obterSessaoSalvaBruta(): Promise<SessaoUsuario | null>` a
  `AuthGateway`: recupera a sessão persistida ignorando a expiração do access
  token (usado para tentar renovação). Retorna `null` se não houver sessão
  alguma.

### Adapter (AuthGatewaySupabase)

- Implementado `obterSessaoSalvaBruta()` usando `client.auth.getSession()` +
  `mapearSessao`, sem o filtro de expiração.
- `obterSessaoSalva()` mantém o filtro de expiração (contrato da interface).

### Application (AutenticarUsuarioUseCase)

- `restaurarSessao()` reescrito:
  - Se `obterSessaoSalva()` retornar sessão válida → persiste/busca usuário e
    retorna (comportamento anterior).
  - Se retornar `null`, busca a sessão bruta:
    - Sem sessão bruta → retorna `null`.
    - Sem `refreshToken` → `logout()` + retorna `null`.
    - Com refresh token → chama `renovarSessao(refreshToken)`; se sucesso e
      usuário existir no SQLite, retorna o usuário; em caso de falha ou sessão
      órfã, `logout()` + retorna `null`.

### Testes

- Gateway: teste `obterSessaoSalvaBruta retorna a sessão mesmo quando o access
  token expirou`.
- Use case: 3 novos testes (renovação bem-sucedida, falha de renovação limpa a
  sessão, sessão sem refresh token limpa a sessão).
- Fakes atualizados: `AuthGatewayFake` (spec e `__tests__/fakes/auth-gateway.fake.ts`)
  com `obterSessaoSalvaBruta`.

### VistoriaContext

- Nenhuma mudança necessária: o boot já chama `restaurarSessao()` e o novo
  fluxo de refresh é interno ao use case.

## D-6 — Teste `.spec.tsx` (concluído por remoção)

### Tentativa da opção (b)

A opção (b) proposta (converter para `.spec.ts` com asserções compatíveis com
`core`) **não funcionou**: `react-native` é ESM e não pode ser `require`-d sob
ts-jest/node, então o teste falha ao importar `Platform` antes de qualquer
asserção (`require(esm)` não suportado na versão de Node em uso).

### Decisão final

O arquivo `__tests__/infra/ui-project.saude.spec.tsx` foi removido, junto com a
tentativa `.spec.ts`. Motivos:

1. O teste é um "health check" de UI que só pode rodar sob `jest-expo/ios`,
   o que exige `@react-native/jest-preset` (conflito de peer-dependência
   documentado em `docs/rastreabilidade.md`).
2. Instalar essa dependência (opção (a)) foi descartado por risco de quebrar o
   harness inteiro (§5.3 — nenhum workaround).
3. Manter um teste que nunca executa (opção (c)) mascara falhas e viola o
   espírito de §4.1 (testes que rodam e são mensuráveis).

### Resultado

- Arquivo removido: `__tests__/infra/ui-project.saude.spec.tsx`.
- `jest.config.js` mantém `testMatch: ['**/__tests__/**/*.spec.ts']` (sem
  `.tsx`).
- Limitação documentada: a verificação do preset `jest-expo/ios` requer uma
  sprint dedicada com instalação de `@react-native/jest-preset` (ou migração
  para EAS/Expo Go).

### Quality gates (D-6)

- `npm run typecheck`: 0 erros
- `npm run lint`: 0 problemas
- `npm test`: 46 suites / 381 testes
- `npm run coverage`: thresholds atendidos
