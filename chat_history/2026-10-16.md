## O que a verificação encontrou

O relatório de 13/10 declarava conformidade. O código dizia outra coisa em cinco
lugares, e **três deles eram afirmações da própria sessão de 13/10**.

### 1. Buraco de contrato — `Evidencia` aceitava evidência sem hash

O hash era obrigatório no contrato da câmera (`ICameraGateway`) desde o Lote 8,
mas o value object mantinha `hash?: string` enquanto o DDL declara
`hash TEXT NOT NULL`. A Fase 1 reidrata a evidência a partir de uma **linha do
banco** — caminho em que o compilador não protege.

### 2. Cópia defensiva ausente em `ItemChecklist`

O Lote 6 declara: *"cópias defensivas na construção e na leitura, em `Vistoria`,
`Ocorrencia`, `ItemChecklist` e `Geolocalizacao`"*.

| Entidade | Construção | Leitura |
|---|---|---|
| `Vistoria` | ✅ `:54` `[...props.itens]` | ✅ `:87` `[...this._itens]` |
| `Ocorrencia` | — | ✅ `:120` `[...this._fotos]` |
| **`ItemChecklist`** | ❌ `:44` `props.evidencias \|\| []` | ❌ `:57` `return this._evidencias` |

O getter devolvia o array interno. `readonly Evidencia[]` só impede `.push()` no
TypeScript — `as Evidencia[]` ou qualquer chamador em JS escreve no agregado. É o
mesmo defeito que a revisão adversarial do Bloco A achou em `Vistoria.itens`,
deixado passar na entidade vizinha.

### 3. `Evidencia.timestamp` era um `Date` mutável exposto

`readonly timestamp: Date` não protege: `readonly` impede reatribuir a referência,
não `setFullYear`. Mesmo motivo do `dataCriacao.setFullYear(1999)` que o Lote 6
corrigiu em `Vistoria` e `Ocorrencia`. **C2 e C3 são a mesma defesa em dois
níveis** — sem o clone, a cópia do array não impede reescrever a data de uma
evidência que está dentro dele.

### 4. `RF-VIST-001` dada como PASS sem existir

`documento-software.md` §4 afirmava PASS para RF-VIST-001..004 e um comentário em
`vistoria.entity.ts:44` citava a regra. Não há guarda nenhuma:
`Vistoria.criar({ status: FINALIZADA })` constrói sem reclamar.

### 5. `RF-VIST-007` descrevia uma regra e implementava outra

A tabela dizia *"Checklist imutável após início da vistoria (itens novos só em
`RASCUNHO`)"*. O código implementa **vistoria finalizada imutável, inclusive na
reidratação**. E a parte escrita não tem implementação porque não existe API de
adicionar item.

## ✅ Risco do `babel.config.js` — VERIFICADO depois

> **Resolvido no terceiro bloco.** O bundle foi montado e saiu limpo.

`babel.config.js` **não existia** e foi criado nesta sessão, mudando o build do
Metro. Os 4 gates **não** o exercitam — `test`, `coverage`, `typecheck` e `lint`
veem TypeScript, Jest e ESLint, e nenhum executa o bundle. Por isso a verificação
foi feita à parte, com cache do Metro limpo:

```
npx expo export --platform ios --clear
→ iOS Bundled 23489ms node_modules/expo-router/entry.js (1500 modules)
→ _expo/static/js/ios/entry-….hbc (3.5MB)   ·  EXIT=0
```

**1500 módulos, 3,5 MB de bytecode Hermes.** O `babel.config.js` não quebra o
build. Este aviso ficou desatualizado no meio da sessão e foi corrigido aqui —
deixá-lo seria a mesma classe de afirmação obsoleta que a sessão se propone a
eliminar.

**Como reverter, se precisar:** apagar `babel.config.js` volta o Metro ao default
anterior — e quebra o project `ui` de novo, porque o arquivo é o que o conserta.

### Auditoria: o Babel está obedecendo a §1.1?

Sim, e a verificação foi feita no código do preset, não por suposição.

O `babel-preset-expo` **tem ramos de web no código**, o que parece violação do
§1.1 à primeira vista. Mas a plataforma não é decidida pelo preset:

```js
function getPlatform(caller) {
  if (caller.platform) return caller.platform;   // quem manda é o bundler
  if (getBundler(caller) === 'webpack') return 'web';
}
```

| Contexto | Caller | Platform |
|---|---|---|
| Jest (`jest-expo/ios`) | `{name:'metro', bundler:'jest', platform:'ios'}` | `ios` |
| Metro | `platform` do projeto | `android` / `ios` |

Só `webpack` cairia em `web`. O projeto não tem webpack, não tem
`react-native-web`, e o `app.json` não declara plataforma web — removida pelo
T-03. E `babel.config.js` contém **apenas** `presets: ['babel-preset-expo']`:
nada de react-native-web, plugin de web ou resolução para browser.

A diferença é entre a ferramenta **suportar** uma plataforma e o app
**direcionar-se** a ela. Não há implementação web no aplicativo.

Também verificado: `expo-router` **não** exige plugin de Babel neste SDK — o
`babel-preset-expo` resolve o router root sozinho, via
`getExpoRouterAbsoluteAppRoot`.

### O risco que sobrou

`expo start --web` é proibido pelo §1.1, e hoje falharia por ausência de plataforma
no `app.json`. Mas **nenhum teste barra** essa regressão. Se alguém rodar
`expo start --web` depois de reintroduzir a plataforma, a lei é violada sem
nenhum gate acusar. É a mesma categoria do C-13: conformidade afirmada, não provada.

## Quinto bloco — Fase 1, passo 2a-i: chave de deduplicação

**RF-SYNC-007.** O DDL exige `chave_dedup TEXT NOT NULL` com índice único, mas
nenhum código produzia a coluna (C-11) — um repositório SQLite que a ignorasse
violaria o `NOT NULL` na primeira inserção, **em produção, não em teste**.

```ts
readonly chaveDedup: string;   // "vistorias:INSERT:vist-1"
this.chaveDedup = `${props.tabela}:${props.operacao}:${props.idRegistro}`;
```

A chave é **derivada, nunca recebida**: nenhum chamador pode esquecê-la nem mandá-la
errada. `DadosOutbox` ganhou `idRegistro` obrigatório — e não `payload.id`, porque
`payload` é `Record<string, unknown>` e essa leitura seria silenciosamente frágil.
`tabela` e `operacao` já existiam, então **não se repetem na chamada**.

| Etapa | O que aconteceu |
|---|---|
| RED | `TS2353: 'idRegistro' does not exist` · `TS2339: 'chaveDedup' does not exist` |
| Contrato | 28 erros de typecheck: 5 use cases, repositório in-memory, 3 specs |
| GREEN | 9 testes de entidade + 3 de fiação do repositório |

**Prova de não-vacuidade por mutação:** passei `idRegistro: 'registro-errado'` no
repositório e exatamente 2 testes falharam
(`Expected "ocorrencias:INSERT:oc-42" / Received "ocorrencias:INSERT:registro-errado"`).
A primeira tentativa de mutação — remover o repasse — quebrou a *compilação*
(`Tests: 0 total`), que é loud mas não prova a asserção; por isso foi refeita com a
mutação que compila. As duas estão registradas porque a primeira resposta, sozinha,
seria enganosa.

**Fora do escopo, de propósito:** `updatedAt` nas entidades. Não bloqueia o passo 2b
e pertence à Fase 3 (last-write-wins). A C-11 agora separa o que foi fechado
(`chave_dedup`) do que falta (`updated_at`, `sync_log`).

**C-16 nasceu aqui:** o índice único global + a chave derivada tornamlegais dois
eventos sobre o mesmo registro colidirem. A decisão (lançar / coalescer / chave por
evento) é do responsável e **bloqueia o passo 2b**.
