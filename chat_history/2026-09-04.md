## Escopo Proposto pelo Usuário

**Ideia original:** Aplicativo móvel de vistoria predial preventiva, gestão de ocorrências e manutenção de condomínios.

**Problema central:** Síndicos e zeladores que realizam inspeções em áreas com "sombra" de sinal (garagens subterrâneas, casas de máquinas, subestações, coberturas) e precisam documentar avarias, manutenções e leituras sem perder dados.

**Casos de uso principais:**
1. Abertura e preenchimento de checklists de vistorias periódicas (elevadores, bombas, extintores, fachada)
2. Registro de chamados e ocorrências com fotos e classificação de gravidade
3. Visualização do histórico de manutenções e status de sincronização no painel local
4. Sincronização automática em segundo plano assim que o dispositivo recuperar o sinal de Wi-Fi ou dados móveis

**Público-alvo:** Síndicos profissionais, síndicos moradores, zeladores e equipes de manutenção predial.

## Fase 1 — Análise de Escopo e Opções

O escopo original foi analisado como contendo ~5 macro-funcionalidades com estimativas de 70–100h, excedendo o budget de 60h.

**Opções de MVP apresentadas:**

### Opção A — "Inspetor Offline" (Recomendada)
- Foco: Fluxo de execução de vistoria com sync offline à prova de falhas
- 4 telas: Lista de Vistorias → Checklist → Foto/Evidência → Fila de Sync
- SQLite local, fila de operações com retry
- Fotos persistidas em `expo-file-system` com upload lazy
- 1 condomínio, 1 usuário, mock backend
- Estimativa: 45–55h

### Opção B — "Chamado Relâmpago"
- Foco: Incidente com foto + severidade
- 3 telas: Lista → Nova Ocorrência → Detalhe
- Estimativa: 30–40h

### Opção C — "Construtor de Checklists"
- Foco: Configuração + execução simples
- Admin cria checklists, inspetor executa
- Estimativa: 55–65h (risco de estourar budget)

### Opção D — "Painel do Síndico"
- Foco: Dashboard visual com mock data
- Estimativa: 20–30h
- Fraco no diferencial offline

**Tradeoff analisado:**
| Critério | A | B | C | D |
|---|---|---|---|---|
| Resolve problema offline | ⭐⭐⭐ | ⭐⭐ | ⭐⭐ | ⭐ |
| Cabe 60h | ⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐ | ⭐⭐⭐ |
| Diferencial vs concorrentes | ⭐⭐⭐ | ⭐⭐ | ⭐⭐ | ⭐ |
| Reutilização entre condomínios | ⭐ | ⭐ | ⭐⭐⭐ | ⭐ |
| Demo impactante | ⭐⭐⭐ | ⭐⭐ | ⭐⭐ | ⭐⭐⭐ |

**Conclusão:** Opção A selecionada como melhor escolha — resolve exatamente o problema de "sombra de sinal", diferencial real vs concorrentes web-first (SíndicoNet, CondApp, Colab, GestãoClick).

## Fase 2 — Validação de Direção Mobile

Pergunta do usuário: *"Como isso seria uma aplicação móvel? Algo para um celular?"*

Resposta: Confirmação de que o app faz todo sentido como app móvel, pois:
- Inspeções acontecem ON SITE (garagem, cobertura, máquina)
- Fotos precisam ser tiradas in loco
- Usuário está andando pelo prédio — celular no bolso
- Offline-first é crítico porque dezenas de locais não têm sinal
- Web/PWA não resolve porque não funciona sem rede, e não é prático em campo

---

## Fase 3 — Restrição Expo Nativo (Sem Web)

**Instrução do usuário:** *"Não pode ser web, deve ser aplicativo Expo. Em NENHUMA situação haverá menção de web."*

**Impacto na avaliação:**
- Opção A (Inspetor Offline): **Fortalecida** — 100% nativo, câmera + SQLite + file system + background fetch
- Opção B (Chamado Relâmpago): **Fortalecida** — câmera + foto + gravidade, tudo nativo
- Opção C (Construtor de Checklists): **Mais difícil** — admin em tela pequena é ruim
- Opção D (Painel do Síndico): **Mais prejudicada** — dashboards são nativo de web

**Stack confirmada (Expo SDK 54):**
- Expo Router 6 (já existe)
- `expo-camera` ou `expo-image-picker`
- `expo-location`
- `expo-sqlite`
- `expo-file-system`
- `expo-network`
- `expo-background-fetch` (para futuras versões)
- `@supabase/supabase-js`
- `zustand` (state management leve)

## Fase 4 — Requisitos Não-Negotiáveis

**Instrução do usuário:** *"Precisamos fortalecer antes de iniciar a proposta. Uso da câmera, geolocalização, offline-first SQLite e sincronismo Supabase, sem 'workarounds' para futuras versões."*

**Requisitos fixos:**
- ✅ Câmera para evidências fotográficas com geotagging
- ✅ Geolocalização (por item ou sessão)
- ✅ Offline-first com SQLite (nenhum dado perdido)
- ✅ Sincronização confiável com Supabase (fila de outbox + retry)
- ❌ Nenhum workaround que exija refatoração futura

**Arquitetura proposta em camadas:**
```
[UI Layer] → React Native + Expo Router 6
     ↓
[Application Layer] → useVistoriaStore (zustand), useSyncService, useMediaService
     ↓
[Persistence Layer] → SQLite (expo-sqlite) + FileSystem (expo-file-system)
     ↓
[Network Layer] → Supabase Client (@supabase/supabase-js)
```

**Decisões para evitar workarounds:**
- SQLite como fonte da verdade (não memória volátil)
- Fila de outbox para garantir entrega eventual ao Supabase
- Retry com backoff exponencial
- Detecção de rede para trigger de sync

**Estimativa revisada (60h):**
| Fase | Foco | Horas |
|------|------|-------|
| Fase 1 — Fundação | SQLite schema, câmera, geolocalização | ~10h |
| Fase 2 — Fluxo Core | Checklist execution + evidências | ~18h |
| Fase 3 — Sync com Supabase | Outbox + retry + detecção de rede | ~15h |
| Fase 4 — Robustez & UX | Indicadores de status, tratamento de erros | ~10h |
| Fase 5 — Polish | Transições, haptics, testes em device real | ~7h |
| **TOTAL** | | **60h** |

**Riscos identificados:**
- Geolocalização imprecisa em garagens subterrâneas
- Sync em background pode ter quirks (Expo background-fetch não 100% confiável)
- Conflitos de sync com múltiplos dispositivos (mitigado: single-device no MVP)
- Tamanho do app com SQLite + fotos (mitigado: compressão de imagens)

**Perguntas em aberto (pendência):**
1. Autenticação: login obrigatório ou anônimo por condomínio?
2. Geolocalização: por sessão ou por item?
3. Sync: manual (botão) ou automático em background desde o dia 1?
4. Supabase: URL/key já disponíveis? Schema definido?
